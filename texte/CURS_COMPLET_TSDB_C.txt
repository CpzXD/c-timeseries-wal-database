CURS PRACTIC DE C: CONSTRUIM O BAZĂ DE DATE TIME-SERIES
Ediția 1 — pentru proiectul tău Windows/MSVC/CMake

Scopul cursului
----------------
Vei construi, pas cu pas, o bibliotecă C și un program în terminal care
stochează puncte de forma (metrică, timp, valoare). Exemplu:
  ("cpu", 1720000000000, 42.5)
Înseamnă: metrica CPU avea valoarea 42.5 la momentul indicat în milisecunde.
Datele trebuie să rămână accesibile după repornirea programului.

Acest document conține trei părți: HARTA explică ideile și ordinea etapelor;
ATELIERUL spune ce fișier deschizi, ce tastezi, de ce și cum verifici. PARTEA III explică testele de oprire a procesului.
Fragmentele de cod sunt pași de învățare. Tu scrii componentele; le
revizuim împreună. Nu lipi toate exemplele în proiect dintr-o dată.

Ce este o bibliotecă C? Este cod pe care îl poate folosi alt program. La noi,
tsdb_core.lib conține funcțiile de bază, iar tsdb.exe le va apela. Testele
apelează aceleași funcții. Compilatorul transformă fiecare fișier .c în cod
obiect; linkerul unește codul cu bibliotecile și produce .exe.

Mic dicționar de C înainte de lecția 1
---------------------------------------
1. Tipuri și variabile
   int x = 7;              // număr întreg
   double v = 1.5;         // număr cu virgulă mobilă
   uint8_t b = 0xFF;      // exact 8 biți, adică un octet
   int64_t t = -1000;      // întreg cu semn, exact 64 de biți
   size_t n = 3;           // tip pentru dimensiuni și indici de memorie

   uint8_t și int64_t vin din <stdint.h>; size_t din <stddef.h> (și alte
   antete standard). Folosim dimensiuni fixe când definim un format pe disc:
   un int simplu nu garantează aceeași lățime pe orice platformă.

2. Tablouri și indici
   uint8_t raw[92] = {0};
   raw[0] = 0x54;

   Avem 92 de celule, numerotate 0...91. raw[92] ar ieși din tablou și este
   o eroare gravă. {0} inițializează toate elementele cu zero.

3. Pointeri
   int x = 7;
   int *p = &x;
   *p = 9;

   &x înseamnă adresa lui x; *p înseamnă valoarea de la acea adresă. După
   exemplu, x este 9. Un pointer poate fi NULL. Înainte de a-l folosi,
   verificăm: if (p == NULL) return TSDB_ERR_ARGUMENT;

4. Structuri
   typedef struct { char metric[64]; int64_t timestamp_ms; double value; }
       TsdbPoint;
   TsdbPoint point = {0};
   point.value = 42.5;

   Structura grupează câmpuri în RAM. Între câmpuri pot exista octeți de
   aliniere puși de compilator. De aceea NU scriem structura brută pe disc.
   Definim separat cei 92 de octeți ai formatului persistent.

5. Funcții și rezultate
   TsdbStatus tsdb_record_encode(const TsdbPoint *point, uint8_t out[92]);

   const înseamnă că funcția nu modifică punctul primit. out este un buffer
   de ieșire furnizat de apelant. Funcția întoarce TSDB_OK la succes sau un
   cod de eroare explicit. În parametri, out[92] se comportă ca un pointer;
   funcția nu poate deduce automat că există 92 de octeți disponibili.

6. Șiruri de caractere
   char name[4] = {'c','p','u','\0'};

   '\0' marchează sfârșitul textului în C. strlen caută acest terminator.
   Pentru date venite din fișier nu presupunem că există; verificăm lungimea
   și limitele înainte să citim mai departe.

7. Copiere de octeți
   memcpy(dest, src, 3);

   memcpy copiază exact 3 octeți; nu adaugă '\0'. Este util pentru biții unui
   double, fiindcă o conversie numerică ar schimba reprezentarea.
   Declarația se află în <string.h>.

8. Condiții și bucle
   if (point == NULL) return TSDB_ERR_ARGUMENT;
   for (size_t i = 0; i < 8; ++i) { /* procesez octetul i */ }

   if execută ramura numai când condiția este adevărată. Bucla de mai sus
   rulează pentru i = 0,1,...,7: exact opt iterații.

9. Biți și little-endian
   Un octet are 8 biți. Pentru numărul 0x0102, little-endian scrie întâi
   0x02, apoi 0x01. Operatorul >> mută biții la dreapta; << la stânga;
   | combină biți. De exemplu:
     raw[0] = (uint8_t)(number >> 0);  // octetul inferior
     raw[1] = (uint8_t)(number >> 8);  // octetul următor
   La citire: number = (uint16_t)raw[0] | ((uint16_t)raw[1] << 8).
   Castează la tipul suficient de lat ÎNAINTE de <<.

10. Checksum și limite
   CRC-32 este o amprentă calculată din octeții recordului. Dacă un octet
   se schimbă accidental, de obicei se schimbă și CRC-ul. CRC detectează
   coruperea accidentală; nu este criptografie și nu dovedește autenticitatea.
   isfinite(v), din <math.h>, respinge NaN și infinitul. Pentru v1 acceptăm
   numai valori finite.

Exercițiu de încălzire, fără să modifici proiectul:
   Pentru numărul 0x1234, scrie pe hârtie cei doi octeți little-endian.
   Răspuns: 0x34, 0x12. Apoi citește-i la loc:
   0x34 | (0x12 << 8) = 0x1234.

## 1. Fundamentele pe care le întâlnim în cod

### 1.1 Bit, octet și hexazecimal

Un bit este 0 sau 1. Opt biți formează un octet. `uint8_t` ocupă exact un octet.
Scriem octeții în hexazecimal: `0xFF` reprezintă 255, iar `0x08` reprezintă 8.
Exemplu: octetul `0x08` este `00001000` în binar.

**De ce:** fișierele conțin octeți, nu structuri C. Pentru a diagnostica o
corupere trebuie să putem arăta exact care octet este greșit.

### 1.2 Variabile, pointeri și structuri

`TsdbPoint` grupează numele metricii, momentul și valoarea. `TsdbPoint *point`
este adresa unui astfel de obiect. `point->value` citește un câmp prin pointer.
`NULL` înseamnă că pointerul nu indică un obiect valid.

**Exemplu:** dacă cineva apelează `encode(NULL, out)`, funcția întoarce
`TSDB_ERR_ARGUMENT` înainte să încerce `point->metric`.

### 1.3 Tipuri cu dimensiune fixă

`uint8_t` = 8 biți fără semn; `uint32_t` = 32; `uint64_t` = 64; `int64_t` = 64
cu semn. `double` ocupă 8 octeți în mediul nostru și păstrează valori reale.
`size_t` este tipul folosit pentru dimensiuni și indici de memorie.

**De ce:** „un `int`” nu este o promisiune suficient de precisă pentru un format
de fișier. Formatul nostru trebuie să însemne același lucru la fiecare citire.

### 1.4 Header, cod sursă, bibliotecă și teste

- `include/tsdb/record.h` declară structuri, constante, erori și funcții.
- `src/record.c` implementează funcțiile.
- `src/main.c` construiește programul `tsdb.exe`.
- `tests/test_record.c` verifică comportamentul.
- `CMakeLists.txt` descrie cum se compilează totul.

Headerul nostru se include cu ghilimele: `"tsdb/record.h"`. Headerurile C
standard se includ cu paranteze unghiulare:

| Header | Folosit pentru | Exemplu |
| --- | --- | --- |
| `<stdint.h>` | numere cu dimensiune fixă | `uint8_t` |
| `<stddef.h>` | dimensiuni și pointer nul | `size_t`, `NULL` |
| `<string.h>` | octeți și memorie | `memcpy`, `memcmp` |
| `<math.h>` | proprietăți numerice | `isfinite` |
| `<stdio.h>` | afișare și fișiere în lecții viitoare | `fprintf` |

MSVC transformă `record.c` în `tsdb_core.lib`; apoi legăm acea bibliotecă la
`tsdb.exe` și `record_tests.exe`. VS Code este editorul, MSVC este compilatorul,
iar CMake descrie procesul de construire.

## 2. Modulul I — Un punct devine 92 de octeți (săptămânile 1–2)

**Întrebarea modulului:** cum păstrăm o măsurătoare într-un format pe care îl
putem recunoaște și verifica mai târziu?

### Lecția 1: definim un contract binar

Un record are 92 de octeți, numerotați 0–91:

| Offset | Octeți | Conținut | Motiv |
| ---: | ---: | --- | --- |
| 0–3 | 4 | ASCII `TSR1` | recunoaștem formatul |
| 4 | 1 | versiune `1` | putem schimba formatul în viitor |
| 5 | 1 | lungimea numelui, 1–63 | știm câte caractere citim |
| 6–7 | 2 | zero | spațiu rezervat, verificabil |
| 8–15 | 8 | timestamp `int64`, little-endian | momentul măsurătorii |
| 16–23 | 8 | biții lui `double`, little-endian | valoarea exactă |
| 24–87 | 64 | numele și zerouri de completare | lungime fixă |
| 88–91 | 4 | CRC-32/IEEE, little-endian | detectăm coruperea accidentală |

**Exemplu:** pentru numele `cpu`, octetul 5 este `03`, iar pozițiile 24–26
conțin `63 70 75` în hexazecimal. Celelalte poziții din zona numelui sunt zero.

**De ce nu `fwrite(&point, sizeof point, ...)`?** Compilatorul poate organiza
structura pentru memorie, inclusiv cu spații de aliniere. Fișierul trebuie să
respecte contractul nostru de 92 de octeți, nu reprezentarea accidentală a
structurii în RAM.

### Lecția 2: validăm datele înainte de codare

Numele acceptă litere ASCII, cifre, `_`, `-` și `.`, are 1–63 caractere și este
terminat cu `\0` în cei 64 de octeți ai structurii. Valoarea trebuie să fie
finită. Pointerii nu pot fi `NULL`.

**Exemple:** `system.cpu.percent` este valid; `cpu percent` nu este; `INFINITY`
nu este o valoare permisă. Parcurgem cel mult 64 de poziții, fiindcă `strlen`
ar putea continua în afara obiectului dacă lipsește terminatorul.

### Lecția 3: scriem octeții în ordine stabilită

Little-endian înseamnă că punem primul octetul cel mai puțin semnificativ.
Numărul demonstrativ `0x0102030405060708` devine:

```text
08 07 06 05 04 03 02 01
```

Pentru `double`, folosim `memcpy` ca să păstrăm biții. O conversie numerică la
`uint64_t` ar transforma `1.5` în `1` și ar pierde informația. `-0.0` și
`0.0` se compară numeric egal, dar au biți diferiți; testul verifică această
diferență.

### Lecția 4: calculăm CRC-ul

CRC-32/IEEE produce un număr de 32 de biți din octeții 0–87. Dacă schimbăm
accidental un octet, CRC-ul recalculat va fi de regulă diferit. CRC-ul nu este
criptare și nu garantează că un atacator nu a modificat datele.

**Exemplu:** pentru recordul de test cu `cpu`, valoarea `1.0` și timestampul
`0x0102030405060708`, octeții CRC de la final sunt `92 EF 69 7A`.

### Lecția 5: decodăm și verificăm

`decode` citește antetul, lungimea și CRC-ul, reconstruiește timestampul și
valoarea și validează numele. Construiește un `TsdbPoint` temporar; schimbă
`out` numai dacă întregul record este corect.

**Exemplu:** dacă schimbăm un bit al valorii la offset 16, antetul rămâne bun,
dar CRC-ul nu mai corespunde. Răspunsul este `TSDB_ERR_CHECKSUM`.

**Starea curentă a proiectului:** `encode` este terminat. În `decode` ai deja
verificarea pointerilor, a semnăturii, a versiunii, a lungimii și a octeților
rezervați. Urmează citirea CRC-ului, recalcularea lui, reconstrucția câmpurilor
și validarea rezultatului. Testele `round_trip` și `corruption` sunt încă roșii
din acest motiv.

**Criteriu de ieșire:** `record_tests.exe` trece; putem explica fiecare octet
și putem demonstra că o intrare coruptă nu modifică obiectul de ieșire.

## 3. Modulul II — Jurnalul de scriere și recuperarea (săptămânile 3–6)

**Întrebarea modulului:** ce se întâmplă dacă programul se oprește în timpul
scrierii?

### Lecția 6: append-only

Deschidem un fișier jurnal (WAL, „write-ahead log”) și adăugăm recorduri la
sfârșit. Nu rescriem punctele vechi în loc. Inițial, un jurnal simplu poate
conține recorduri de 92 de octeți unul după altul.

**Exemplu:** trei măsurători ocupă trei recorduri consecutive. Dacă ultima
scriere se oprește după 40 de octeți, la repornire citim primele două recorduri
complete și recunoaștem finalul incomplet.

### Lecția 7: citire la pornire și erori de disc

La `open`, parcurgem jurnalul, verificăm fiecare record și reconstruim starea
din memorie. Distingem un final tăiat de un record corupt aflat la mijloc:
primul se poate ignora conform regulii de recuperare; al doilea trebuie raportat
ca eroare, nu ascuns.

**Exemplu:** `bun | bun | 40 de octeți` se recuperează până la ultimul record
complet. `bun | CRC greșit | bun` este o corupere internă și deschiderea eșuează.

### Lecția 8: scrieri confirmate și batchuri atomice

`write_batch` va scrie mai multe puncte ca o singură operație logică. Pentru
asta, jurnalul va primi o încadrare a batchului și un marcaj de commit. La
recuperare, un batch fără marcaj complet nu devine vizibil.

**Exemplu:** batchul conține trei puncte; procesul cade după al doilea. După
repornire nu trebuie să vedem doar două puncte dintr-un batch care trebuia să
fie atomic. Vom testa oprirea în fiecare loc important.

Un răspuns de succes vine numai după sincronizarea jurnalului cu sistemul de
operare. Pe Windows vom învăța ce garantează `FlushFileBuffers`; simpla
întoarcere dintr-o funcție de scriere nu este aceeași promisiune. Chiar și așa,
nu pretindem protecție absolută față de orice defect al discului sau controlerului.

**Criteriu de ieșire:** un batch confirmat apare după repornire; un batch
neconfirmat nu apare parțial; erorile de scriere sunt raportate.

## 4. Modulul III — Index în memorie și reguli pentru duplicate (săptămânile 7–9)

**Întrebarea modulului:** cum găsim `cpu` fără să recitim fiecare punct `ram`?

### Lecția 9: organizăm punctele după metrică

Pornim cu o structură simplă: fiecare metrică are o colecție de puncte.
Învățăm alocare dinamică, capacitate, realocare, ownership și eliberarea
memoriei. Limita de memorie este explicită; la eșec de alocare întoarcem eroare.

**Exemplu:** `cpu` are 100 de puncte, `ram` are 100. O interogare pentru `cpu`
nu mai parcurge și cele 100 de puncte `ram`.

### Lecția 10: ordine temporală și date întârziate

Punctele pot sosi în afara ordinii: primim timestampurile 10, apoi 30, apoi 20.
Interogarea trebuie să le arate 10, 20, 30. Începem cu o soluție simplă și
măsurăm când trebuie un index mai eficient.

### Lecția 11: duplicate

Cheia logică a unui punct este `(metrică, timestamp)`. Dacă aceeași cheie se
scrie din nou, câștigă ultima **scriere confirmată**. Păstrăm o ordine internă
a commiturilor pentru a decide asta și după repornire.

**Exemplu:** `cpu@10 = 20`, apoi `cpu@10 = 25`; interogarea întoarce 25.

**Criteriu de ieșire:** indexul reconstruit din WAL dă același rezultat ca
indexul dinaintea închiderii, inclusiv pentru puncte întârziate și duplicate.

## 5. Modulul IV — Interogări și agregări (săptămânile 10–12)

### Lecția 12: intervale de timp

Implementarea folosește `query_range(metric, start, end)` cu interval
`[start, end]`: includem ambele limite. Pentru intervale alăturate trebuie
să alegem limite care nu dublează același timestamp.

**Exemplu:** punctele la 10, 20, 30; `[10, 30]` întoarce toate trei punctele.

### Lecția 13: agregări

Calculăm `count`, `min`, `max` și `avg` numai peste punctele din interval.
Definim explicit rezultatul pentru zero puncte: `count = 0`, iar celelalte
agregări sunt zero. Apelantul verifică `count` pentru a distinge un interval
gol de un interval care conține valoarea zero.

**Exemplu:** valorile 10, 20, 30 au `count=3`, `min=10`, `max=30`, `avg=20`.

### Lecția 14: CLI

CLI-ul primește comenzi precum `init`, `write`, `query`, `stats` și `check`.
Biblioteca rămâne separată: CLI-ul traduce textul utilizatorului în apeluri C.
Testăm și intrări greșite, de exemplu timestamp invalid sau interval inversat.

**Criteriu de ieșire:** interogările coincid cu un model simplu de referință,
inclusiv pentru metrici inexistente, intervale goale și valori duplicate.

## 6. Modulul V — Segmente imuabile pe disc (săptămânile 13–17)

**Întrebarea modulului:** cum evităm ca jurnalul și memoria să crească la
nesfârșit?

### Lecția 15: flush din memorie într-un segment

Scriem punctele vechi în fișiere noi, sortate după metrică și timestamp. Un
segment terminat nu se modifică. Păstrăm metadate precum intervalul de timp și
metricile conținute.

**Exemplu:** dacă un segment conține doar date din ianuarie, o interogare din
martie îl poate sări complet.

### Lecția 16: indexul segmentului

Adăugăm un index rar: la intervale regulate notăm poziția unor blocuri din
fișier. Căutăm mai întâi în index, apoi citim doar blocurile relevante.

**Exemplu:** pentru 1 milion de puncte, nu începem fiecare căutare la octetul
zero al fișierului.

### Lecția 17: stare persistentă și checkpoint

Un manifest indică segmentele active și locul sigur până la care datele din WAL
au fost mutate. Întâi scriem și verificăm noul segment, apoi schimbăm starea
activă. Nu ștergem jurnalul vechi înainte ca noua stare să fie recuperabilă.

**Exemplu:** procesul cade după ce segmentul a fost scris, dar înainte de
activarea lui. La repornire folosim manifestul anterior și WAL-ul; datele nu
dispar.

**Criteriu de ieșire:** interogările combină corect memoria și segmentele,
fără dubluri, iar un restart în timpul flushului nu pierde scrieri confirmate.

## 7. Modulul VI — Compactare și retenție (săptămânile 18–21)

### Lecția 18: compactare

Mai multe segmente mici devin unul mai mare. La îmbinare păstrăm ultima
versiune confirmată pentru aceeași metrică și același timestamp.

**Exemplu:** primul segment are `cpu@10=20`, al doilea are `cpu@10=25`;
segmentul compactat conține valoarea vizibilă 25.

### Lecția 19: schimbare sigură a segmentelor

Scriem fișiere noi separat, le verificăm, actualizăm manifestul și abia apoi
eliminăm fișierele vechi. Vom testa opriri între fiecare două operații. Pe
Windows, înlocuirea și sincronizarea fișierelor cer atenție specială.

### Lecția 20: retenție

O regulă precum „păstrează ultimele 30 de zile” calculează un prag temporal.
Punctele mai vechi dispar logic și sunt eliminate fizic la compactare. Nu
ștergem un întreg segment dacă el conține și date care trebuie păstrate.

**Criteriu de ieșire:** rezultatele sunt aceleași înainte și după compactare,
cu excepția punctelor expirate; spațiul vechi este recuperat în siguranță.

## 8. Modulul VII — Validare, măsurare și demo (săptămânile 22–26)

### Lecția 21: teste de crash

## 9. Cum arată viitoarea interfață

Biblioteca va avea operații de forma:

```text

write_batch(puncte[]) → confirmare sau eroare
```

metrici locale pe echipamente Windows care rămân offline sau auditul datelor
într-un laborator. Abia apoi decidem dacă merită un installer, dashboard,
serviciu sau suport plătit. Un benchmark bun nu dovedește singur că există
clienți.

## Laboratorul 1 — Formatul binar al unui punct

**Fișiere:** `include/tsdb/record.h`, `src/record.c`, `tests/test_record.c`.

### 1.1 Contractul funcției

În `record.h` există:

```c
TsdbStatus tsdb_record_encode(const TsdbPoint *point,
                              uint8_t out[TSDB_RECORD_SIZE]);
```

În C, parametrul `out[TSDB_RECORD_SIZE]` se comportă aici ca un pointer la
primul octet. `point` este `const`: funcția citește punctul, dar nu îl schimbă.
`TsdbStatus` spune dacă a reușit sau de ce nu a reușit.

**Exemplu:** `encode(NULL, raw)` trebuie să întoarcă `TSDB_ERR_ARGUMENT`.
Nu avem voie să încercăm `point->metric` când `point == NULL`.

### 1.2 Ce înseamnă un offset

Recordul are 92 de octeți, `record[0]` până la `record[91]`. Offsetul este
numărul poziției de la început. De exemplu, `&record[24]` este adresa de la
care începe numele metricii. Pentru `cpu`, copiem 3 octeți de acolo:

```c
memcpy(&record[24], point->metric, name_length);
```

`memcpy(destinație, sursă, număr_de_octeți)` copiază exact câți octeți cerem.
Nu caută automat `\0` și nu știe că datele sunt text.

### 1.3 De ce scriem little-endian manual

În record, timestampul ocupă pozițiile 8–15. Pentru fiecare octet `byte`
din 0–7, punem octetul corespunzător al numărului:

```c
record[8 + byte] = (uint8_t)(timestamp_bits >> (8 * byte));
```

`>>` mută biții spre dreapta; conversia la `uint8_t` păstrează ultimii 8 biți.
Pentru `0x0102030405060708`, primul octet scris este `08`, apoi `07`, până la
`01`. Aceasta este o decizie a **formatului nostru**, nu ceva ce lăsăm la
alegerea compilatorului.

Pentru valoarea `double`, folosim `memcpy` către un `uint64_t` înainte de
mutări. Așa păstrăm biții lui `1.5` sau `-0.0`; un cast numeric ar pierde
informație.

### 1.4 Unde ești acum

În codul tău, `encode` validează intrarea, scrie toate câmpurile, calculează
CRC-ul și întoarce `TSDB_OK`. Testul cu layoutul exact trece. `decode` verifică
deja pointerii, `TSR1`, versiunea, lungimea numelui și octeții rezervați.

**Următoarea bucată de tastat în `src/record.c`:** în funcția
`tsdb_record_decode`, după verificarea `in[6]` și `in[7]`, citește CRC-ul
stocat:

```c
uint32_t stored_crc =
    (uint32_t)in[88] |
    ((uint32_t)in[89] << 8) |
    ((uint32_t)in[90] << 16) |
    ((uint32_t)in[91] << 24);

(void)stored_crc; /* doar până la exercițiul următor */
```

**De ce:** la `encode` ai împărțit un număr de 32 de biți în patru octeți.
Acum îi unești la loc. `<<` mută octetul la poziția sa; `|` combină părțile.
Conversia la `uint32_t` înaintea mutării împiedică operații nedorite pe un
`int` cu semn. Dacă octeții sunt `92 EF 69 7A`, numărul reconstruit este
`0x7A69EF92`.

**Verificare:** compilează. Testele `round_trip` și `corruption` vor rămâne
roșii; încă nu comparăm CRC-ul. `(void)stored_crc` ține compilatorul mulțumit
temporar.

### 1.5 Recalculezi CRC-ul

În `decode`, calculează CRC-ul din `in[0]` până la `in[87]`, folosind aceeași
buclă pe care o ai în `encode`. Diferența este sursa octeților: `in[pos]` în
loc de `record[pos]`. După complementarea finală, compară:

```c
if (computed_crc != stored_crc) {
    return TSDB_ERR_CHECKSUM;
}
```

Elimină `(void)stored_crc`. Dacă cineva a schimbat un octet al valorii, noul
CRC diferă de cel stocat. Dacă `TSR1` este greșit, funcția întoarce mai întâi
`TSDB_ERR_FORMAT`, fiindcă verificarea antetului se află înaintea CRC-ului.

**Verificare:** rulează `.\build\Debug\record_tests.exe`. Testul
`test_corruption` trebuie să treacă; `test_round_trip` încă așteaptă citirea
câmpurilor. După ce funcționează, vom extrage calculul CRC într-o funcție
privată comună pentru `encode` și `decode`, ca să avem o singură implementare.

### 1.6 Reconstruiești timestampul și valoarea

Pentru timestamp, pornești de la un `uint64_t` zero și adaugi fiecare octet:

```c
uint64_t timestamp_bits = 0;
for (size_t byte = 0; byte < 8; byte++) {
    timestamp_bits |= ((uint64_t)in[8 + byte]) << (8 * byte);
}
```

`|=` înseamnă `timestamp_bits = timestamp_bits | ...`. Conversia la `uint64_t`
se face înainte de `<<`, altfel mutarea cu 56 de biți nu ar încăpea într-un
`int` obișnuit. Repeți ideea pentru valoare, folosind `in[16 + byte]`.

Copiază **biții** în câmpurile unui `TsdbPoint` temporar cu `memcpy`. Pentru
timestampul negativ evităm o conversie nesigură dintr-un `uint64_t` prea mare
în `int64_t`; copierea biților păstrează reprezentarea de pe platforma noastră.

### 1.7 Reconstruiești numele și termini `decode`

Ia `name_length = in[5]`. Copiază numai acei octeți din `in[24]` în
`temp.metric`, apoi pune `temp.metric[name_length] = '\0'`. Verifică faptul că
octeții rămași din zona 24–87 sunt zero și că fiecare caracter copiat respectă
regula numelui. Verifică și `isfinite(temp.value)`.

```c
TsdbPoint temp = {0};
/* reconstruiești câmpurile și le validezi aici */
*out = temp;
return TSDB_OK;
```

**De ce obiect temporar?** Dacă recordul este invalid, funcția iese înainte de
`*out = temp`; obiectul primit de la apelant rămâne intact.

**Criteriu de ieșire:** toate testele din `record_tests.exe` trec. Mai adăugăm
teste pentru nume invalid în fișier, padding nenul și trunchiere înainte de a
folosi recordul pentru date reale.

## Laboratorul 2 — Primul fișier și jurnalul de scriere

**Scop:** înțelegi diferența dintre „am format un record” și „l-am salvat
sigur”. Lucrăm în `src/wal.c`, `include/tsdb/wal.h`, `tests/test_wal.c`, pe care
le vom crea după Laboratorul 1.

### 2.1 Exercițiu de învățare: scrie și citește un record

Într-un mic test temporar, deschizi un fișier binar, encodezi un punct și scrii
exact 92 de octeți. Modelul operațiilor este:

```c
uint8_t raw[TSDB_RECORD_SIZE];
/* verifici că tsdb_record_encode(&point, raw) == TSDB_OK */
/* deschizi fișierul în mod binar pentru scriere */
size_t written = fwrite(raw, 1, sizeof raw, file);
/* verifici că written == sizeof raw și verifici fclose */
```

**De ce `fwrite(raw, 1, sizeof raw, file)`?** Argumentele sunt „dimensiunea
unei unități” și „numărul de unități”; cu unitate de 1 octet, rezultatul este
numărul de octeți efectiv scriși. O scriere scurtă este eroare.

**Exemplu:** două recorduri complete ocupă 184 de octeți. Un fișier de 130 de
octeți conține unul complet și un început de al doilea.

Acesta este **un exercițiu**, nu forma finală a WAL-ului. `fclose` și `fflush`
nu sunt contractul nostru final de durabilitate și nu avem încă batchuri atomice.

### 2.2 Citește înapoi și tratează finalul incomplet

Într-o buclă, încerci să citești 92 de octeți. Dacă obții 92, apelezi
`decode`. Dacă obții 0 și ai ajuns la EOF, jurnalul s-a terminat normal. Dacă
obții între 1 și 91 la final, ai o ultimă scriere incompletă.

```c
size_t got = fread(raw, 1, sizeof raw, file);
if (got == sizeof raw) {
    /* decode și procesează */
} else if (got == 0 && feof(file)) {
    /* sfârșit normal */
} else {
    /* eroare de citire sau coadă incompletă: distinge cu ferror/feof */
}
```

**De ce distincția?** O citire scurtă poate însemna finalul fișierului sau o
eroare I/O; nu vrem să ascundem o problemă reală.

### 2.3 Forma finală: batch atomic

Un jurnal format doar din recorduri nu spune dacă un batch de trei puncte a
fost terminat. Vom defini un cadru binar explicit:

```text
BEGIN:  magic TBG1 (4) + count uint32 LE (4) + sequence uint64 LE (8)
DATA:   count × recorduri TSR1 de 92 de octeți
COMMIT: magic TCM1 (4) + sequence uint64 LE (8) + CRC32 LE (4)
```

CRC-ul de COMMIT acoperă întregul BEGIN și DATA. În `wal.h` vom declara
operațiile `wal_append_batch` și `wal_replay`. Nu scriem structurile C direct
în fișier; codăm fiecare câmp la offsetul stabilit, ca la `record`.

**Exemplu:** procesul cade după al doilea punct dintr-un batch de trei.
Lipsește COMMIT-ul valid, deci la repornire ignorăm întregul batch. Dacă COMMIT
este valid, aplicăm toate cele trei puncte o singură dată. Impunem o limită
maximă pentru `count` înainte de alocare, ca un fișier corupt să nu ceară o
cantitate uriașă de memorie.

### 2.4 Când putem spune „scriere confirmată”

Pe Windows, `FlushFileBuffers` solicită scrierea datelor tamponate ale unui
fișier. În componenta Windows de I/O vom folosi handle-uri și vom verifica
fiecare rezultat al operațiilor de deschidere, scriere și flush. `write_batch`
întoarce `TSDB_OK` doar după scrierea completă și flushul COMMIT-ului.

**Exemplu:** dacă `WriteFile` raportează mai puțini octeți decât am cerut sau
`FlushFileBuffers` eșuează, apelul întoarce eroare, nu succes. Nu promitem
rezistență la orice defect fizic al unității de stocare.

**Teste:** jurnal gol, un batch, două batchuri, ultimul batch tăiat la fiecare
offset important, CRC greșit în mijloc, eroare I/O simulată. Testele de crash
vin în Laboratorul 7.

## Laboratorul 3 — Indexul din memorie

**Fișiere:** `src/index.h`, `src/index.c`, `tests/test_query.c`.

### 3.1 Prima reprezentare

Începem cu o colecție de serii. O serie înseamnă toate punctele cu același
nume de metrică. În interiorul seriei avem puncte și numărul commitului care
le-a făcut vizibile.

```c
typedef struct {
    TsdbPoint point;
    uint64_t sequence;
} TsdbEntry;

typedef struct {
    TsdbEntry *items;
    size_t length;
    size_t capacity;
} TsdbVector;
```

`length` este numărul folosit, `capacity` este spațiul alocat. Pentru început
căutarea metricii poate fi liniară; o optimizăm numai când măsurătorile arată
că merită.

### 3.2 Creșterea unui vector

Modelul sigur pentru `realloc` este:

```c
if (vector->length == vector->capacity) {
    size_t next = vector->capacity == 0 ? 16 : vector->capacity * 2;
    TsdbEntry *grown = realloc(vector->items, next * sizeof *grown);
    if (grown == NULL) {
        return TSDB_ERR_NO_MEMORY;
    }
    vector->items = grown;
    vector->capacity = next;
}
vector->items[vector->length++] = entry;
```

**De ce pointer temporar `grown`?** Dacă `realloc` eșuează și am scrie direct
rezultatul în `vector->items`, am pierde adresa memoriei vechi. În implementare
verificăm și că `capacity * 2` și `next * sizeof` nu depășesc `SIZE_MAX`.
Adăugăm `<stdlib.h>` pentru `realloc` și `free`.

### 3.3 Puncte întârziate și duplicate

Exemplu de sosire: timestampurile 10, 30, 20. La interogare le prezentăm
10, 20, 30. Pentru aceeași pereche `(metric, timestamp)`, păstrăm valoarea din
ultimul batch confirmat: `cpu@10=20`, apoi `cpu@10=25` → răspunsul este 25.

**Ce scrii:** funcții pentru căutarea unei serii, adăugare, sortare/căutare și
eliberarea completă a memoriei. Nu publicăm o schimbare dintr-un batch în
index înainte de COMMIT-ul confirmat.

**Teste:** insert în ordine, insert întârziat, duplicate, `realloc` eșuat prin
injectare, reconstrucție din WAL.

## Laboratorul 4 — Interogări și agregări

**Fișiere:** `include/tsdb/tsdb.h`, `src/tsdb.c`, `src/main.c`, `tests/test_query.c`.

### 4.1 API-ul public

Un API înseamnă funcțiile pe care alt program are voie să le apeleze. Avem
un tip opac `Tsdb`: utilizatorul primește un pointer, dar nu poate modifica
direct structurile interne.

```c
typedef struct Tsdb Tsdb;
TsdbStatus tsdb_open(const char *path, Tsdb **out_db);
TsdbStatus tsdb_write_batch(Tsdb *db, const TsdbPoint *points, size_t count);
TsdbStatus tsdb_query_range(Tsdb *db, const char *metric,
                            int64_t start_ms, int64_t end_ms,
                            TsdbPoint **out_points, size_t *out_count);
void tsdb_free_points(TsdbPoint *points);
TsdbStatus tsdb_close(Tsdb *db);
```

**De ce `Tsdb **out_db`?** Funcția trebuie să schimbe pointerul apelantului,
nu doar o copie locală a lui. Vom documenta cine deține memoria returnată și
cine o eliberează. Codurile de eroare includ argument invalid, I/O, format,
checksum, lipsă memorie și bază ocupată.

### 4.2 Intervalele `[start, end]`

Condiția este `timestamp >= start_ms && timestamp <= end_ms`. Ambele limite
sunt incluse, iar `[30, 30]` poate căuta exact timestampul 30.

**Exemplu:** avem puncte la 10, 20, 30. `[10, 30]` întoarce toate trei punctele.
Pentru două rezultate alăturate fără dubluri alegem `[10, 29]` și `[30, 40]`.

### 4.3 `count`, `min`, `max`, `avg`

Pentru 10, 20, 30 obținem 3, 10, 30, 20. Actualizăm media progresiv:

```c
count++;
double divisor = (double)count;
mean += value / divisor - mean / divisor;
```

**De ce:** formula permite o medie fără să păstrăm separat toate valorile și
evită, în multe cazuri, un total intermediar foarte mare. Pentru zero puncte,
`count=0`, iar `min/max/avg` sunt zero; `count` indică lipsa valorilor.

### 4.4 CLI-ul

`main.c` va parsa comenzi text și va apela API-ul. Exemple de interfață
planificată:

```text
tsdb init data
tsdb write data cpu.percent 1727532000000 42.5
tsdb query data cpu.percent 1727532000000 1727535600000
tsdb aggregate data cpu.percent 1727532000000 1727535600000
```

Vom folosi `strtoll` și `strtod`, verificând că întregul argument a fost
consumat și că nu apare overflow. CLI-ul afișează mesaje de eroare clare.

**Teste:** interval gol, metrică inexistentă, timestamp invalid, `start > end`,
duplicate, medie cu valori pozitive și negative.

## Laboratorul 5 — Segmente imuabile pe disc

**Fișiere noi:** `src/segment.c`, `include/tsdb/segment.h`, teste de segment.

### 5.1 Ce problemă rezolvăm

WAL-ul și indexul activ nu pot crește la infinit. La un prag controlat scriem
un **segment**: puncte sortate după `(metrică, timestamp, sequence)`. După ce
segmentul a fost finalizat, nu îl modificăm.

**Exemplu:** segmentul A conține ianuarie, segmentul B martie. O interogare
doar pentru martie poate sări A după ce citește intervalele din antet.

### 5.2 Primul segment

Începem cu un fișier simplu: un antet cu magic/versiune/count și un șir de
recorduri. Scriem într-un fișier temporar, verificăm fiecare `fwrite`, îl
sincronizăm și abia apoi îl declarăm activ în manifest. Nu scriem un `struct`
direct pe disc; fiecare câmp din antet primește offset și ordine a octeților.

**Ce scrii:** comparatorul pentru `qsort`, writerul de segment, readerul și
verificarea antetului. Exemplu de criteriu pentru comparator: întâi `strcmp`
pentru metrică, apoi compararea timestampurilor fără scădere (scăderea a două
`int64_t` ar putea face overflow), apoi `sequence`.

### 5.3 Index rar

După ce citirea secvențială funcționează, păstrăm offsetul fiecărui bloc de,
de exemplu, 256 de puncte. Pentru o căutare sărim la blocul relevant și citim
doar o parte din fișier. Acesta este un **index rar**; nu avem nevoie de o
intrare în index pentru fiecare punct.

**Exemplu:** dintr-un milion de puncte, indexul ne duce lângă intervalul
cerut, în loc să citim de la primul punct.

### 5.4 Manifestul și checkpointul

Manifestul listează segmentele active și poziția WAL până la care datele sunt
deja în segmente. La repornire citim manifestul și refacem din WAL doar datele
mai noi. Actualizarea manifestului trebuie să fie recuperabilă: scriem o
versiune nouă, o verificăm, o sincronizăm, apoi o activăm.

**Exemplu de crash:** segmentul nou există, dar manifestul vechi este încă
activ. La repornire folosim manifestul vechi și WAL-ul; segmentul incomplet
activat nu poate face datele să dispară.

**Teste:** 0/1/multe puncte, segment tăiat, index greșit, crash înainte și
după activarea manifestului, interogări care unesc indexul activ cu segmentele.

## Laboratorul 6 — Compactare și retenție

**Fișiere:** `src/compaction.c`, CLI `compact`, teste de integrare.

### 6.1 Îmbinarea a două segmente sortate

Ținem câte un cursor în fiecare segment. Comparăm cheile curente, emitem
cheia mai mică și avansăm cursorul potrivit. Dacă găsim aceeași pereche
`(metrică, timestamp)`, păstrăm intrarea cu `sequence` mai mare.

```text
A: cpu@10=20, cpu@30=40
B: cpu@10=25, cpu@20=35
rezultat: cpu@10=25, cpu@20=35, cpu@30=40
```

**De ce:** după compactare, interogarea citește mai puține fișiere și dublurile
vechi nu mai ocupă spațiu. Testăm că rezultatele interogărilor sunt identice
înainte și după compactare.

### 6.2 Schimbarea sigură a fișierelor

Ordinea logică este: creează segment nou → termină și verifică scrierea →
activează manifestul nou → șterge segmentele care nu mai sunt active. Dacă
procesul se oprește între pași, manifestul arată ce fișiere sunt autoritare.
Pe Windows vom verifica operațiile de înlocuire a fișierelor și tratarea
erorilor, fără să presupunem că un simplu `rename` rezolvă orice caz.

### 6.3 Retenția

Definim un prag temporal: `cutoff_ms = now_ms - retention_ms`, verificând
overflow. Punctele mai vechi de prag nu apar în interogări și sunt eliminate
fizic la compactare. Luăm timpul de referință ca parametru în teste, ca testul
să nu depindă de ceasul real.

**Exemplu:** păstrăm 30 de zile; un punct de acum 31 de zile expiră, unul de
acum 29 de zile rămâne.

**Teste:** segmente cu date de ambele părți ale pragului, duplicate, crash la
fiecare etapă a activării, spațiu eliberat numai după activare sigură.

## Laboratorul 7 — Crash, performanță și demonstrație

### 7.1 Testezi ce se întâmplă când procesul moare

Un program de test pornește un proces copil, îi cere să scrie un batch și îl
oprește forțat la puncte controlate: după BEGIN, la jumătatea DATA, după
COMMIT, după flush. Repornește baza și verifică toate batchurile confirmate.

**De ce:** închiderea normală a programului nu simulează un crash. Un test
fiabil trebuie să forțeze oprirea când operația este incompletă.

### 7.2 Compari cu un model simplu

Pentru teste, păstrezi într-o structură simplă din memorie răspunsul corect.
Generezi multe operații, le aplici atât modelului, cât și bazei tale, apoi
compari interogările. Modelul poate fi lent: rolul lui este corectitudinea.

**Exemplu:** 10.000 de puncte aleatorii, inclusiv timestampuri întârziate și
duplicate, trebuie să dea aceleași rezultate după restart și compactare.

### 7.3 Măsori fără să te păcălești

Notezi puncte/secundă, timp de interogare, timp de deschidere și spațiu pe
disc. Fiecare rezultat include numărul de puncte, mărimea batchului, tipul
discului și politica de flush. Fără aceste detalii, două cifre de performanță
nu sunt comparabile.

### 7.4 Adaugi un colector Windows

Colectorul este separat de motor. Pentru RAM, o lecție va folosi
`GlobalMemoryStatusEx` și va scrie metrici precum `system.ram.used_bytes`.
Pentru CPU citim două eșantioane ale timpilor sistemului și calculăm o
diferență; un singur eșantion nu dă procentul CPU.

**Demo final:** pornești colectorul, aduni date, închizi și redeschizi baza,
interoghezi un interval, rulezi compactarea și arăți testele de crash.

PARTEA III — RECUPERAREA DUPĂ OPRIREA PROCESULUI

# Lecție: ce se întâmplă dacă programul este oprit brusc?

Am adăugat `tests/test_wal_crash.c`. El pornește un proces copil, îl oprește
forțat într-un moment controlat și redeschide baza în procesul părinte.
Build-ul Debug cu `/W4 /WX` a reușit, iar toate cele **9 teste CTest** trec.
Testul nou conține **8 scenarii**. Numărul testelor nu este numărul asserturilor.

## 1. De ce avem nevoie de acest pas?

Până acum verificam fișiere incomplete și erori de scriere simulate.
Mai trebuia să verificăm recuperarea atunci când dispare chiar programul
care ține baza deschisă. Dacă apelăm `tsdb_close`, programul are ocazia să
închidă normal resursele. În testul nou, copilul nu apelează această funcție:
părintele îl termină cu `TerminateProcess`.

Exemplu: programul scrie `cpu@1000 = 10`, primește succes, apoi este oprit.
La redeschidere, această valoare trebuie să existe.

## 2. Ce înseamnă proces părinte și proces copil?

Un proces este o instanță a unui program aflată în execuție. Pornim de două
ori același executabil, `wal_crash_tests.exe`:

```text
PĂRINTE: creează scenariul -> pornește copilul -> așteaptă semnalul
COPIL:   creează WAL-ul -> scrie -> semnalizează -> așteaptă
PĂRINTE: oprește copilul -> redeschide WAL-ul -> verifică rezultatul
```

Copilul este pornit cu argumentul `--child`. În `main`, această opțiune îl
trimite în `child_main`; fără argumente, executabilul rulează testele părintelui.
Fiecare proces are propria memorie. După oprirea copilului, părintele nu poate
folosi indexul din memoria acestuia: indexul trebuie reconstruit din fișier.

## 3. Ce date scriem?

Primul lot este confirmat întotdeauna:

| Metrică | Timestamp | Valoare |
|---|---:|---:|
| cpu | 1000 | 10 |
| ram | 2000 | 20 |

Al doilea lot conține:

| Metrică | Timestamp | Valoare | Ce verificăm |
|---|---:|---:|---|
| cpu | 1000 | 99 | Înlocuirea unei valori existente |
| cpu | 500 | 5 | Un punct sosit în afara ordinii |
| ram | 3000 | 30 | Un punct pentru altă metrică |

Dacă lotul al doilea este incomplet, după reparare trebuie să găsim doar
primul lot. Chiar dacă recordul `cpu@1000 = 99` este complet, el aparține
unui lot fără COMMIT complet. Valoarea veche, 10, trebuie să rămână vizibilă.
Nu aplicăm separat fiecare record întâlnit în coada incompletă.

Dacă lotul al doilea este complet și valid, interogarea CPU trebuie să dea
punctele `cpu@500 = 5`, apoi `cpu@1000 = 99`. Media lor este 52.
Pentru RAM avem 20 și 30, cu media 25.

## 4. Cum calculăm dimensiunile?

Folosim formatul WAL v2:

```text
Antet fișier: 16 octeți
BEGIN:        20 octeți
Un record:    92 octeți
COMMIT:       16 octeți
```

Primul lot are două puncte: `20 + 2 × 92 + 16 = 220` octeți.
Cu antetul fișierului: `16 + 220 = 236` octeți.
Al doilea lot are trei puncte: `20 + 3 × 92 + 16 = 312` octeți.
Fișierul cu ambele loturi complete are `236 + 312 = 548` octeți.

În cod, aceste formule sunt constantele `BASELINE_BATCH_SIZE`,
`PENDING_BATCH_SIZE`, `BASELINE_FILE_SIZE` și `MAX_FILE_SIZE`.
Nu numărăm octeții unei structuri C: folosim dimensiunile formatului pe disc.

## 5. Cum alegem exact momentul opririi?

Am adăugat `tsdb_wal_test_pause_write` în headerul intern
`src/wal_fault_hooks.h`. Funcția spune copiei de test a WAL-ului:

```text
La următoarea scriere, scrie N octeți reali în fișier,
apoi apelează funcția de pauză.
```

În `append_write_all`, ramura de test scrie prefixul cu `WriteFile`, apoi
apelează `test_checkpoint`. Restul lotului ar fi scris dacă funcția de pauză
s-ar întoarce. În aceste scenarii copilul rămâne în pauză până este terminat.
O pauză de 0 octeți înseamnă oprire înainte de scrierea următorului BEGIN.

`TsdbWalTestCheckpoint` este un **pointer la funcție**: în loc să stocăm un
număr, stocăm funcția care trebuie apelată la acel moment.
`void *context` transportă adresa handle-ului evenimentului. Funcția
`signal_and_wait` citește handle-ul și trimite semnalul către părinte.
Adresa rămâne validă deoarece variabila copilului există pe durata apelului.

Părintele și copilul comunică printr-un eveniment Windows. Copilul apelează
`SetEvent` abia după ce prefixul a fost scris. Părintele așteaptă evenimentul
sau ieșirea copilului cu `WaitForMultipleObjects`. Nu ghicim momentul opririi
printr-o întârziere de două secunde.

În scenariul după confirmare, copilul folosește API-ul public
`tsdb_write_batch`, așteaptă `TSDB_OK`, apoi trimite semnalul.

## 6. Cele opt scenarii

Numărul din coloana a doua este câți octeți există din al doilea lot.

| Momentul opririi | Octeți noi | Lungime WAL | Rezultat la deschidere |
|---|---:|---:|---|
| După succesul `tsdb_write_batch` | 312 | 548 | Ambele loturi |
| Înainte de următorul BEGIN | 0 | 236 | Doar primul lot |
| În timpul BEGIN | 7 | 243 | `TSDB_ERR_INCOMPLETE` |
| La jumătatea primului record | 66 | 302 | `TSDB_ERR_INCOMPLETE` |
| După primul record complet | 112 | 348 | `TSDB_ERR_INCOMPLETE` |
| Înainte de COMMIT | 296 | 532 | `TSDB_ERR_INCOMPLETE` |
| La jumătatea COMMIT | 304 | 540 | `TSDB_ERR_INCOMPLETE` |
| După COMMIT, înainte de flush și succes | 312 | 548 | Ambele loturi în acest test |

Pentru fiecare coadă incompletă verificăm că deschiderea nu modifică niciun
octet. Apoi `tsdb_repair` trebuie să creeze un backup identic cu fișierul
inițial și să elimine exact prefixul lotului al doilea. Comparăm efectiv
octeții backupului, nu doar lungimea lui. Prefixul confirmat trebuie să rămână
identic, iar interogările și agregările trebuie să redea valorile așteptate.

După recuperarea cu un singur lot, adăugăm din nou lotul al doilea prin API,
închidem și redeschidem. Astfel verificăm și că baza poate continua să scrie,
iar secvențele WAL rămân valide. Repararea unui fișier fără coadă este un
no-op: nu elimină octeți și nu creează backup.

## 7. COMMIT complet și confirmare către apelant

Acestea sunt două momente diferite. COMMIT este o structură din fișier.
Confirmarea către apelant înseamnă că funcția a terminat sincronizarea
cu `FlushFileBuffers` și a întors `TSDB_OK`.

Poate exista următoarea ordine:

```text
BEGIN + recorduri + COMMIT au fost scrise
programul este oprit înainte de flush și înainte să întoarcă succes
Windows continuă să ruleze
redeschiderea găsește lotul complet și valid
```

Recuperarea nu poate afla dacă apelantul a văzut succesul. Ea poate verifica
octeții, secvența și CRC-urile. De aceea un lot fără răspuns primit poate fi
vizibil integral la redeschidere. Un lot incomplet nu este aplicat parțial.
Lipsa confirmării nu înseamnă automat că datele lipsesc.

Testul oprește un proces și lasă Windows în funcțiune, inclusiv cache-ul
sistemului. El nu demonstrează recuperarea după o pană de curent. Scenariul
înainte de flush verifică tocmai această limită a confirmării.

## 8. Ce fac funcțiile Windows din test?

| Funcție sau constantă | Rol în test |
|---|---|
| `CreateProcessA` | Pornește propria copie a executabilului |
| `CREATE_NO_WINDOW` | Copilul nu deschide o fereastră de consolă |
| `CREATE_SUSPENDED` | Copilul așteaptă până configurăm gestionarea lui |
| `CreateJobObjectW` / `AssignProcessToJobObject` | Atașează copilul unui job |
| `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE` | Oprește copilul dacă părintele dispare și handle-ul jobului se închide |
| `ResumeThread` | Permite copilului să înceapă după atașarea la job |
| `CreateEventA` / `OpenEventA` / `SetEvent` | Creează, deschide și semnalizează evenimentul de sincronizare |
| `TerminateProcess` | Oprește forțat procesul copil creat de test |
| `WaitForSingleObject` | Așteaptă ieșirea procesului înainte să citim fișierul |
| `GetExitCodeProcess` | Confirmă că oprirea a folosit codul stabilit de test |
| `CloseHandle` | Eliberează resursele Windows deținute de părinte |

Copilul are maximum 10 secunde să ajungă la pauză. CTest are și o limită
totală de 30 de secunde. Fiecare scenariu folosește un director temporar
separat. După succes este șters; după o eroare păstrăm fișierele și afișăm
directorul pentru diagnostic.

Macro-ul `CHECK` sare la eticheta `cleanup` când o verificare eșuează.
În aceste teste, această cale eliberează rezultatele interogărilor, închide
baza sau oprește copilul, după funcția în care ne aflăm. Scopul este ca o
verificare eșuată să nu lase un proces pornit sau un fișier blocat.

## 10. Cum rulezi tu?

În terminalul PowerShell:

```powershell
Set-Location -LiteralPath 'C:\Users\username\Documents\baza de date in C'
cmake -S . -B build
cmake --build build --config Debug
ctest --test-dir build -C Debug --output-on-failure
```

`cmake -S . -B build` actualizează proiectele de compilare cu noul executabil.
`cmake --build` compilează sursele. `ctest` rulează executabilele deja compilate.
Rezultatul verificat este `100% tests passed out of 9`.

Pentru a vedea fiecare scenariu:

```powershell
.\build\Debug\wal_crash_tests.exe
```

Pentru a rula numai testul nou prin CTest:

```powershell
ctest --test-dir build -C Debug -R '^wal_process_crash$' --output-on-failure -V
```

`-R` selectează numele testului; `-V` afișează inclusiv mesajele `PASS`.

## 12. Unde suntem în roadmap?

Avem formatul recordului, WAL-ul și interogările etapei 3. Am verificat acum
și recuperarea după terminarea forțată a procesului, o parte din validarea
prevăzută în etapa 6. Urmează etapa 4: formatul segmentelor imuabile pe disc.

Tot indexul actual se află încă în RAM, iar WAL-ul crește. Segmentele vor
permite citirea datelor vechi de pe disc. Înainte să activăm un segment,
trebuie să proiectăm manifestul, secvențele pentru duplicate și publicarea
sigură după crash. Testele noi nu încheie validarea întregului motor:
compactarea, retenția, erorile de alocare și erorile din backup mai cer lucru.
